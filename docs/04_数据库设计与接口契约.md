# 数据库设计与接口契约（v2 · 全栈版）

> 本文件是**实现的唯一事实来源（SSOT）**。任何字段、错误码、事务边界的改动必须先改本文件。
> 运行环境：Node.js ≥ 22.5（内置 `node:sqlite`，本项目实测 v24.21.0 可用），**零 npm 依赖**。

---

## 一、设计原则

1. **所有写入必须落到 SQLite**。前端不再使用 localStorage 存业务数据（仅保留纯 UI 偏好，如表格筛选）。
2. **数值规则只有服务端一个可信来源**：点数领取、扣除、@ 冷却、每日重置全部在服务端计算并记流水。
3. **每个写接口都在事务里**：内容创建与点数扣减同事务提交，失败整体回滚。
4. **资源路径规范化**：头像/媒体统一由服务端 `/media/...` 提供，客户端只认服务端返回的 URL，任何失败都有默认兜底。
5. **权限边界由服务端强制**，前端只做体验层隐藏。

## 四、状态机

### 4.1 @ 呼叫

```
用户发帖/回复含 @某高管
        │
        ▼
   [职级与风控预检]  ← 服务端同步执行
        │
   ┌────┴─────────────────────────────┐
   │ 预检通过                          │ 预检不通过
   ▼                                  ▼
 status=pending                    status=rejected（直接终态）
 回执：审核中文案                    回执：未通过文案
        │
        ▼（后台审核 worker，约 3–10s）
 status=under_review ← 回执：审核中文案（若前端尚未拿到）
        │
        ▼ 价值评估
   ┌────┴─────────────┐
   │ 判定有价值         │ 判定无价值
   ▼                   ▼
 status=approved     status=rejected
 回执：通过文案        回执：未通过文案
 + 转阅（生成高管回帖）
```

**预检不通过条件**（任一命中即驳回）：

| 条件 | 判定依据 | 是否可配置 |
|---|---|---|
| 同一用户 60 秒内重复呼叫同一位高管 | `mentions` 最近一条同 user+officer | 是（`mention.cooldown_sec`） |
| 同一用户 1 小时内呼叫总次数超限 | `mentions` 计数 | 是（`mention.hourly_limit`） |
| 单帖呼叫高管数超过上限 | 本次请求内去重后计数 | 是（`mention.max_per_post`） |
| 呼叫的正文有效长度 < 15 字 | 内容长度 | 否（质量门槛） |
| 同一用户 24 小时内呼叫过同一位高管 | `mentions` 存在记录 | 否（防刷屏） |
| 呼叫对象 `enabled = 0` | `ai_officers` | — |

**价值评估通过条件**（全部满足才通过）：

| 条件 |
|---|
| 正文有效长度 ≥ 30 字 |
| 正文不含纯灌水模式（连续重复字符 ≥ 8） |
| 近 10 分钟该用户呼叫次数 ≤ 2 |

**`<time>` 动态计算**（不得写死）：

```
base = 8 分钟
+ 正文长度 ≥ 120 字 ? 4 : 0
+ 该高管近 1 小时被呼叫次数 * 2   （上限 +12）
+ 职级差修正：max(0, officer.authority_level - requester_level) * 2
→ 夹紧到 [5, 45] 分钟
assigned_at = now + minutes*60_000
```
前端把 `assigned_at` 渲染为「预计 ${HH:mm} 前后转阅」，并与分钟数一起展示。

### 4.2 入职与岗位变更

```
注册 → users.status = pending_onboarding
     → POST /api/requests {type:'onboarding', payload:{department_id, job_role_id}}
     → 管理员面板审批
        ├─ approved：写 users.department_id/job_role_id，status=active，employment_status=hired
        └─ rejected：写 review_note，用户可重新提交
已 active 员工改岗位 → type='job_change'/'dept_change' → 同样走管理员审批
```

## 五、错误码

统一响应体：

```json
{ "ok": false, "error": { "code": "INSUFFICIENT_POINTS", "message": "…", "details": {} } }
```

| code | HTTP | 含义 | 前端处理 |
|---|---|---|---|
| `BAD_REQUEST` | 400 | 参数校验失败（`details.fields` 给出字段级错误） | 行内红字 |
| `UNAUTHORIZED` | 401 | 未登录 / 会话过期 | 跳登录 |
| `FORBIDDEN` | 403 | 已登录但无权 | 提示无权 |
| `NOT_FOUND` | 404 | 资源不存在 | 空态/404 |
| `CONFLICT` | 409 | 唯一约束（账号重复、部门重名、今日已领取） | 字段提示 |
| `INSUFFICIENT_POINTS` | 402 | 余额不足（`details.balance/required`） | 提示差额 + 去领取 |
| `RATE_LIMITED` | 429 | 限流（`details.retryAfter` 秒） | 倒计时提示 |
| `MENTION_COOLDOWN` | 429 | @ 冷却中（`details.retryAfter`） | 倒计时提示 |
| `MENTION_INVALID_TARGET` | 400 | 呼叫对象不存在/已停用 | 提示 |
| `ONBOARDING_REQUIRED` | 403 | 未完成入职手续 | 引导进入职流程 |
| `PAYLOAD_TOO_LARGE` | 413 | 上传超限 | 提示体积上限 |
| `UNSUPPORTED_MEDIA` | 415 | 头像格式不支持 | 提示格式 |
| `INTERNAL` | 500 | 服务端异常（带 `traceId`） | 通用错误提示 |

## 六、接口清单

约定：所有接口返回 `{ ok: true, data: … }` 或 `{ ok:false, error:{…} }`；鉴权用 HttpOnly Cookie `haavk_sid`；写接口校验同源 Origin。

## 七、固定文案常量（**不得改动，不得拼接后缀**）

> 以下三段文案为需求硬约束，集中定义于 `server/constants.js` 的 `MENTION_COPY`，**代码中禁止出现第二处副本**。

| 分支 | 常量键 | 文案 |
|---|---|---|
| 审核中 | `UNDER_REVIEW` | `检测到对集团高级管理人员的呼叫.....正在确认呼叫者职级是否足以支撑该行为...正在评估应答时间和问题价值.....` |
| 通过 | `APPROVED` | `已确认该问题值得高管关注，已计算高管为此分配的最合理时间：<time>。已自动转阅。` |
| 未通过 | `REJECTED` | `经哈夫克首席高级秘书办审核讨论，本贴无需转载，请勿短时间内大量呼叫集团高级职员` |

`<time>` 由 `renderApprovedCopy(minutes)` 在渲染回执时替换，格式为 **`N分M秒`**（例：`2分31秒`），
N/M 来自 4.1 节的分钟计算（服务端同时返回结构化的 `assignedLabel`，前端只做展示）。
文案本身在插入数据库前即已渲染完成，**存储的即是最终文案**，不存在二次拼装。

## 八、事务边界（必须严格遵守）

| 操作 | 事务内容 | 失败处理 |
|---|---|---|
| 注册 | 校验唯一 → `INSERT users` → `INSERT points_ledger(signup_bonus)` → `INSERT requests(onboarding)` | 任一步失败整体回滚，返回首个错误码 |
| 领取点数 | `INSERT daily_claims`（唯一约束是防重关键）→ `UPDATE users.points_balance` → `INSERT ledger` | 唯一冲突 → `CONFLICT`，**不加点** |
| 发帖 | 校验余额 → `INSERT posts` → `UPDATE users.points_balance` → `INSERT ledger(-50)` → 解析 @ → `INSERT mentions` + `INSERT receipts` | 余额不足 → 抛错回滚，**不产生帖子** |
| 回复 | 同发帖（-100），并 `UPDATE posts.reply_count/last_reply_*` | 同上 |
| @ 审核通过 | `UPDATE mentions` → `INSERT receipts` → `INSERT replies`（高管转阅回复）→ 高管账号记账 | 整体回滚 |
| 管理员审批入职 | `UPDATE requests` → `UPDATE users(status/department/job)` → `INSERT audit_logs` | 整体回滚 |

并发安全：`db.js` 暴露 `withTx(fn)`，内部使用 `BEGIN IMMEDIATE`，杜绝两个并发扣点同时读到同一余额。

## 九、对账与自愈

`server/tools/reconcile.js`：

1. 对每个用户计算 `SUM(points_ledger.delta)` 与 `users.points_balance` 比较；
2. 对每个用户的 `daily_claims` 检查同一 `(user_id, claim_date)` 是否唯一（由唯一索引保证，此处二次验证）；
3. 对每个帖子校验 `reply_count` 与实际 `replies` 行数；
4. 输出差异清单，`--fix` 参数可按流水修正余额。

验收时**必须先跑对账脚本且输出 0 差异**。
